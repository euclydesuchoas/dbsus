# DbSus — design decisions

Why the library is built the way it is, and what was learned about the files it reads. Entries that are not settled yet are marked **open** or **to validate**.

DbSus is an independent project, not affiliated with the Brazilian Ministry of Health or DATASUS.

## Scope

- Read the `.dbc` (compressed dBase) and `.dbf` files that DATASUS distributes, from .NET, with no external tools: no R, no Python, no native binaries, no P/Invoke.
- Two packages from one repository:
  - `DbSus`: DBC decompression and DBF reading (`DbSus.Dbc`, `DbSus.Dbf`, and the `DbSus` facade).
  - `DbSus.Client`: listing and downloading files from the DATASUS FTP server, with an optional local cache.
- `DbSus.Dbc` and `DbSus.Dbf` do not reference each other, not even in XML doc `cref`s; only the `DbSusFile` facade knows both. The package could be split later without breaking users.
- Not in scope: writing DBC files, a source generator, a command-line tool.

## Architecture

- **Targets:** `netstandard2.0`, `net472` and `net10.0` for both packages. `net472` exists because .NET Framework applications using the `netstandard2.0` build hit a `System.Memory` binding conflict (`FileLoadException`, no automatic binding redirect); `net462` lacks `DbColumn`, so 4.7.2 is the minimum .NET Framework. There is no `net8.0` target: `netstandard2.0` covers it.
- **Dependencies:** none on `net10.0`. `System.Memory` on `net472`; `System.Memory` and `System.Text.Encoding.CodePages` on `netstandard2.0`. The client adds FluentFTP on every target and `Microsoft.Bcl.AsyncInterfaces` on `net472` and `netstandard2.0`. Only the client takes a third-party dependency.
- **Minimum dependency versions:** the packages declare the lowest versions that work (`System.Memory` 4.5.3, `System.Text.Encoding.CodePages` 4.4.0, `Microsoft.Bcl.AsyncInterfaces` 1.0.0), so an application that already references an older version does not hit a downgrade error (NU1605). `System.Memory` 4.5.0 and 4.5.1 fail on .NET Framework (`FileLoadException` for `System.Runtime.CompilerServices.Unsafe`). `src/Directory.Packages.props` lowers these versions for the libraries only; tests and benchmarks use current versions.
- **Encodings:** the library never calls the global `Encoding.RegisterProvider`; it uses `CodePagesEncodingProvider.Instance` locally (on .NET Framework, `Encoding.GetEncoding`), with no side effect on the host process.
- **Strong naming:** both assemblies are strong-named with the committed `DbSus.snk` (public key token `31b7992898fa311e`), following Microsoft's guidance for open-source libraries. The key pair, private part included, is public on purpose: the strong name gives the assemblies a stable identity, which .NET Framework uses to load and bind them, and is not a security mechanism, so it says nothing about who built a binary. The key never changes; a test pins the token.
- **Versioning:** `AssemblyVersion` is `Major.Minor.0.0` during 0.x (every 0.x minor may break) and major-only from 1.0. Releases stay 0.x/preview until the API settles.
- **The client depends on the core within one minor version.** `DbSus.Client` declares `DbSus` as `[its own version, next minor-a)` (`[0.1.0, 0.2.0-a)` for 0.1.0) during 0.x, and up to the next major from 1.0 on, because a 0.x minor may break the API and a later core restored next to an older client could then fail at run time. The bound ends in `-a` so that the previews of the next line are left out too: `0.2.0-preview.1` sorts below `0.2.0`, and every release label that starts with a letter (`alpha`, `preview.1`, `rc.1`) sorts at or above `a`. It is not `-0`, which would also leave out the labels that start with a digit: nuget.org refuses a version whose release label is a single identifier that does not start with a letter (a rule kept for the NuGet 2.x clients), and it rejected the client 0.1.0-preview.3, which declared `[0.1.0-preview.3, 0.2.0-0)`; this repository never uses labels that start with a digit. The package consumers job also runs `tools/nuspec-check`, which checks every version of the packed nuspecs against the rules of nuget.org. The two packages keep the same version. Packing a project reference gives a minimum only, so a target in `src/DbSus.Client/DbSus.Client.csproj` rewrites the range, and a step of the package consumers job checks it in the packed nuspec, since the target relies on an item of the NuGet pack targets. What NuGet does with the range, checked with packages built for the purpose: an application that references a later core directly gets warning NU1608 and the later core is used; only a later core asked for by another dependency fails the restore, with NU1107; with a plain `[version, 0.2.0)`, the previews of 0.2.0 would be accepted without a warning. The client 0.1.0-preview.2, already published, keeps a minimum without an upper bound.

## The files

### DBC layout

Confirmed on every file examined:

- `[0, H)`: the DBF header, verbatim (`H` is the header length at offset 8, UInt16 little-endian).
- `[H, H + 4)`: CRC-32 (zlib/IEEE) of the **whole uncompressed DBF**, little-endian.
- `[H + 4, end)`: a PKWare DCL implode stream. Every DATASUS file seen uses uncoded literals and a 4 KiB dictionary. Nothing follows the end code.
- The DBF is the header plus the decompressed body. Its size is `H + records × record length`, plus a trailing 0x1A end-of-file marker in some sources (present in SIA-PA, absent in SIH-RD and CNES). Both are accepted, and bytes are preserved as stored.

### Checksum is the arbiter

- The stored CRC-32 decides whether a decompressed file is right, not an oracle. In one CNES file (`ST`, Roraima, 2023-01) the last header byte is 0x00 where a 0x0D field terminator is expected; DbSus keeps the byte and matches the stored CRC, while `pyreaddbc` 2.0.4 rewrites it to 0x0D and does not. Oracle hashes are checked against the stored CRC before being accepted.
- Because the CRC covers the whole DBF, a mismatch can only be reported after the last byte has been read.

### DBF dialect seen across sources

Twenty files across SIM, SINASC, SINAN, SIH, SIA and CNES were examined in aggregate (no individual values recorded). Here "examined" means their headers, and counts over their data, such as which field types and which bytes occur. It does not mean "read", which in these notes is reading a file record by record with the DbSus reader: that was done later, for 111 of the 112 file types of the catalog (`docs/datasus-paths.md` says, in its tables, what was read of each; of SINAN-INFL the server had no file to read). The files read of the 54 that are not of SINAN had only `C` and `N` fields. The 65 SINAN files read had `C` fields in every file, `D` fields in all but one (`HANTBR99.dbc`), `N` fields in all but seven, and one field of type `F` in one file (`SRCBR26.dbc`).

- **Header:** field descriptors end at 0x0D, at an empty name, or where the header length runs out (the CNES file above has no terminator at all). Spare bytes after the last field are tolerated; in every file examined the fields fill the record exactly.
- **Field types:** `C` everywhere, `N` in most sources, `D` only in SINAN; no `F`, `L` or `M`. That is of the twenty files examined; of the files read later, one SINAN file had a field of type `F` (above).
- **Numbers:** left-padded with spaces, decimal point `.`, digits after the point as declared. No negatives, no `*` overflow, no blank `N` values seen in the twenty files examined. In October 2026, 12 of the 65 SINAN files read had `N` and `D` fields filled with `*` from end to end in some or all records (66 fields), and one of them also a `D` field with groups of two digits separated by `/` (12 records) and an `N` field with a letter (2 records). The reader throws `FormatException` on such a field unless `DbfReadOptions.UnconvertibleValues` says to read it as null; `GetRawBytes` returns its bytes. The paths guide lists the files and the fields.
- **Dates in character fields** use `YYYYMMDD` in SIH, SIA and CNES but `DDMMYYYY` in SIM and SINASC; they cannot be inferred from field names.
- **Opaque bytes:** some identifier fields (in CNES professional and SIA APAC/BI/PS files) hold bytes above 0x7F that are not text in any code page, so raw access to field bytes is needed.
- **Deletion flag:** blank on every record examined.
- **File names:** some files use an upper-case extension (`.DBC`).

### Language driver (LDID) and code pages

- Values seen, in the headers of the files examined: 0x00 (no driver) in SIM, SINASC, SINAN, SIH SP/ER, SIA AM/AQ/PS and CNES SR/ST; 0x02 in SIH RD/RJ; 0x03 in SIA PA/BI; 0x57 in SIA AD/AR; 0x58 in CNES EQ/LT/PF/HB. The files read later, one of each file type of the catalog, had the same values, and added 0x00 in SIA ATD/ACF and 0x58 in CNES DC/EP/EF/GM/IN/RC. The seven read after them had 0x57 in SIA AB/AN and CIHA, 0x03 in SIA ABO, 0x00 in SIA SAD/AMP and 0x58 in CNES EE. The eleven file types for the whole country only, read in October 2026, had 0x00, except 0x35 in SIM-DOREXT, 0x03 in PO and 0x02 in SIHSUS-MT. Of the 65 SINAN files read in October 2026, 52 had 0x00, seven 0x58 (those of DENG, FMAC and MENT, and the four of COLE), five 0x57 (five of the six of TETN) and one 0x25 (`PESTBR16.dbc`). Reading a file record by record does not check its text: for 0x57 (SIA AD and AR) and for CNES PF and HB the value says which code page is declared, and no text was looked at.
- Meaning: 0x02 = code page 850 and 0x03 = 1252 (Microsoft's Visual FoxPro table); 0x58 = 1252, 0x57 = ISO-8859-1 and 0x59 = 1252 (dBASE drivers, per the MiraMon documentation and GDAL's LDID table).
- 0x35 was seen in four SIM files: one of 2024, in a real-world test in early October 2026, whose record names neither the file nor its folder; the preliminary SIM-DO file of Roraima for 2026; and, in the folders of final data, the SIM-DO file of Roraima for 2020 and `DOREXT20.dbc`. It is in neither table, so the text is read with the fallback, code page 1252, as with 0x00. No text was looked at. In the two SIM-DO files of Roraima, of 2020 and of 2026, no field of any record has a byte above 0x7F, so there the code page makes no difference. On 2026-10-13 it was also seen in `DOAC2023.dbc`, a SIM-DO file of final data, and in `DOREXT25.dbc`; neither has a byte above 0x7F in any field.
- 0x25 was seen in one SINAN file (`PESTBR16.dbc`, 4 records). It is not in the library's map either, so the text is read with the fallback, code page 1252. Its meaning was not looked up, and no text was looked at.
- **What the bytes show (counted in October 2026, never read as text).** In eighteen files of twelve file types of the catalog, the bytes above 0x7F of every character field were counted and classed under code pages 1252, 850, 437 and ISO-8859-1; three identifier fields known to hold bytes that are not text were left out. Text with such bytes was found in four files. One SIHSUS-RD file marked 0x02 had 294 of them in one field, every one a letter Portuguese uses under 850 and none under 1252. Two SIASUS-PA files marked 0x03 had 1,230 in one field, every one a letter of Portuguese under 1252. One CNES-ST file with 0x00 had four in one field: three letters of Portuguese and one symbol under 1252, four box-drawing characters under 850. The other fourteen files had none, so for them the code page changes nothing: one SIASUS-PS file with 0x00; one CIHA, one SIASUS-AD and one SIASUS-AR file marked 0x57; two CNES files marked 0x58; three SIM-DO files and one SIM-DOREXT file with 0x35; one SINAN file with 0x25; and one more SIHSUS-RD file and two more SIASUS-PA files.
- **In the tables of the auxiliary archives the LDID does not tell the code page.** The same count was made on 2026-10-13 over 368 distinct DBF tables found inside archives of auxiliary files of the server (conversion tables and registers for tabulation, which are not file types of the catalog). Under one LDID they hold text of either family. Of the tables marked 0x00 with enough such bytes, nine read as 1252 and six as 850, the six holding two thirds of the bytes. Eleven tables marked 0x02 read as 1252, and fifteen marked 0x03 read as 850. The tables marked 0x57 (26 of 28) and 0x58 (104 of 107) read as 1252, which ISO-8859-1 equals from 0xA0 up; the others mix both families in one table. DbSus reads each of these tables with the code page of its LDID, so some of them come out with the wrong characters and no error: for a table of those archives, look at the text and set `DbfReadOptions.Encoding`.
- **To validate:** the 1252 fallback for LDID 0x00 in files of the catalog, where four bytes in one file are all the evidence; and the code page of files marked 0x57, 0x58, 0x35 and 0x25, in which no text with a byte above 0x7F was seen.

### Split tables (SIA-PA)

- Among the file types surveyed (the SIASUS, SIHSUS, CNES, SIM, SINASC and SINAN data folders listed on the server in October 2026), only SIA-PA is split into lettered parts, `a` to `d`. The headers of all 740 parts of the 307 split groups in `SIASUS/200801_/Dados` (fetched with range requests) were compared, and so were the two parts of one month held locally: no gaps, no group starting after `a`, never an unlettered file next to lettered parts, and all 434 part-to-part comparisons (433 among the files on the server, 1 between the local parts) identical (names, types, widths, decimals, record and header length, LDID, version). The layout changes over time, but never within a month. The rule is therefore strict: identical schema.
- SIA-BI is split in another way: numbered files (`_1`, `_2`, `_3`) in MG, RJ and SP, in every month from 2023-05 on: 257 files of 117 tables in the listings of October 2026, 30 of the tables with a file without a number beside them. For one table (RJ, 2023-06) the headers were compared: the record counts of `_1` and `_2` add up to the one of the file without a number, with the same 36 fields. The headers of `BIMG2312_1.dbc` and `BIMG2312_2.dbc` are identical in what the reader compares (fields, record and header length, LDID, version). One numbered part was read whole; no complete set was.
- SIA-BI has files with a `_1`, `_2` or `_3` suffix (in MG, RJ and SP, from 2023-05: 117 state-months), in 30 of them next to a file without a suffix. Only their names were seen, in the same listing; their content was not examined, and DbSus does not treat them as parts of one table.

### FTP server

- `ftp.datasus.gov.br`, anonymous, IIS. Supports `SIZE`, `MDTM` (UTC, seconds), `REST STREAM`, `EPSV`/`PASV` (in October 2026 its `FEAT` reply did not list `EPSV`, which it accepted). No `MLSD`: only DOS-format `LIST` (two-digit years, minute precision). No TLS: the `FEAT` reply lists `AUTH TLS`, but `AUTH TLS` is refused with `534 Local policy on server does not allow TLS secure connections.` (tried once, October 2026).
- Public files live under `/dissemin/publicos/` (e.g. `SIHSUS/200801_/Dados/RD{UF}{YYMM}.dbc`, `SIASUS/200801_/Dados/PA{UF}{YYMM}{part}.dbc`).
- **Files are republished** under the same name with different content, so anything cached or pinned must be keyed on size and modification time (or a hash), not on the name.
- **No HTTP(S) mirror:** the FTP host does not answer on ports 80/443. The website's download page uses undocumented, form-driven endpoints that return HTML; the library does not use them.

## API and behavior

- **Parameters after a release.** An optional parameter and its default value are compiled into the caller, so a new parameter comes as a new overload, never as one more optional parameter of an existing method, which would break binary compatibility; and a default value does not change unless the changelog announces it as a breaking change.

### Naming

- Parameter names follow one rule: an options parameter is `options` when the method takes one kind (`DbfReader`, `DbcFile`) and `dbfOptions` / `dbcOptions` when it takes both (`DbSusFile`, `DatasusClient`); a stream is named after its format (`dbf`, `dbc`); paths are `path` / `paths`, or `dbcPath` / `dbfPath` when a method takes two; the parts of a split table are `parts`. Renaming a parameter breaks callers that pass it by name, so the names are settled before the first release.

### DBC

- `DbcFile.OpenAsDbf(path | Stream)` returns a read-only, forward-only stream that decompresses on demand. The DBF header and checksum are read at open, so an invalid file fails immediately; the input is read strictly sequentially (network streams work).
- `DbcFile.ConvertToDbf(paths | streams)`: the path overload writes to a temporary file and moves it into place only after success, checksum included; the stream overload writes as it goes.
- Options are an object (`DbcReadOptions`, `DbfReadOptions`), not boolean parameters, so new options do not change signatures. `VerifyChecksum` is on by default.
- The one boolean parameter is `leaveOpen`, the last parameter of every method that takes a stream: who owns a stream is decided per call, not per options object. With `leaveOpen: false` (the default) the stream belongs to DbSus from the call on: it is disposed with the returned reader or stream, and also if the call throws, so `Open(File.OpenRead(path))` never leaks. With `leaveOpen: true` it is never disposed. Methods that take paths open and close their own files; `DbcFile.ConvertToDbf(Stream, Stream)` never disposes either stream.
- Checksum failures are `InvalidDataException` (a sealed type, so there is no subclass); `DbcReadOptions.ChecksumMismatch` is the hook for reacting to them specifically. The callback receives a `DbcChecksumMismatch` (part index and name, stored and computed CRC-32), a class so it can grow without breaking callers.
- The decoder is pull-based and can suspend mid-copy, so callers can read in blocks of any size.
- **No cap on the decompressed size.** A `.dbc` can expand about 170 to 190 times: measured with the test encoder, a copy of 518 bytes costs 24 bits with the 4 KiB dictionary (172.7:1), 23 with the 2 KiB one (180.2:1) and 22 with the 1 KiB one (188.4:1). In the 10 real files checked in October 2026 (CNES, SIASUS and SIHSUS), the decompressed size was exactly the one the header implies, header plus records, with or without a final 0x1A byte. The decompressor still puts no cap computed from the header: the header comes from the same file, so such a cap does not protect against a hostile file, and it could reject a legitimate file not yet seen. Memory stays constant; a limit on the output is the caller's (see Security in the README). The alternative kept for when someone asks for it is an option, `DbcReadOptions.MaxDbfLength` (`long?`, null by default), an addition to the API.

### DBF reader

- One type: `DbfReader : DbDataReader`, usable with `DataTable.Load`, `SqlBulkCopy` and Dapper. Not thread-safe; the inherited async methods complete synchronously.
- **Types:** `C` → `string`; `N` without decimals → `int` (width ≤ 9), `long` (≤ 18), `decimal` (wider); `N` with decimals and `F` → `decimal`; `D` → `DateTime`; `L` → `bool`. Unsupported types (e.g. memo) are exposed as raw bytes and flagged, never as text.
- **Nulls:** blank `N`/`F`/`D`/`L`, `?` in `L` and all-zero dates are `DBNull`; blank `C` is `""` unless `BlankStringsAsNull`. Trailing spaces are trimmed, leading spaces kept.
- **Errors** are `FormatException` naming the field, the record and the part, never the value, because DATASUS data can be personal. For `N`, `F` and `D` fields the message points at `DbfReadOptions.UnconvertibleValues`.
- **Content that does not convert** (`DbfReadOptions.UnconvertibleValues`, for `N`, `F` and `D` fields): `Throw`, `AsterisksAsNull` or `Null`. *Why three values:* in the SINAN files read in October 2026, 66 of the 68 fields that did not convert were filled with asterisks, a mark that can be recognized, and the other two held content of another nature (a date with slashes, a letter in a number). `AsterisksAsNull` reads the first without silencing the second; `Null` is for who wants every record, whatever it holds. *Why the default is `Throw`:* reading such content as null is a guess about what it means (no document that was read says that the asterisks stand for a value that is missing), and a value read as null cannot be told from a blank field; that choice is the caller's. *Why there is no counter:* the option must cost nothing on the default path and stay small; who needs to know what a field holds, and how often, reads it with `GetRawBytes`, which is the same in every mode. *Why `L` fields and converted `C` fields are outside it:* no file read had such content in them, and the conversion of a `C` field is already a choice of the caller, with an error of its own. Read as null is, in every member, what a blank field is. The option is looked at only where a conversion has already failed; in `IsDBNull` of numeric and date fields, in the two modes that read null; and, with `Null`, where an integer field is read as a wider number, so that a number that does not fit its field is null for every getter. In the default mode `IsDBNull` of a numeric field still only tells whether the field is blank: it returns `false` for content that does not convert, and the getter that follows throws.
- **No allocation per record** for `Read` and the typed getters (including `GetFieldValue<T>`; measured on .NET 8, 9 and 10 and on .NET Framework 4.8.1; its nullable forms box on every call on .NET 8, 24 bytes or 32 for `decimal?`, and on .NET Framework, about 24 bytes, because of the runtime's JIT, not the package build). A test guards it. `GetChars` decodes straight into the caller's buffer when the encoding is single-byte (as are the code pages of the LDIDs found in DATASUS files), so text can be read without allocating too; with a double-byte code page (932, 936, 949, 950) or another multi-byte encoding it allocates like `GetString`.
- **Access:** names ignore case; unknown names and ordinals throw `IndexOutOfRangeException` (ADO.NET contract); `TryGetOrdinal` does not throw. `Columns` projects and re-indexes fields. Deleted records are skipped unless requested. `DbfField.FileIndex` is the position in the file, not the ordinal, which counts only the exposed fields.
- **Checksum through the facade:** after the last record the reader drains the decompressed stream, so the `Read` that returns `false` is the one that reports a checksum mismatch.

### Character field conversions

- Opt-in, per field: `DbfFieldConversion.Int32()`, `Int64()`, `Decimal()` and `Date("yyyyMMdd" | "ddMMyyyy")`, only on `C` fields, validated at open. A converted field reports its target type everywhere; blank is null; a value that does not parse or does not fit is a `FormatException` (field, record and part, never the value).
- `Date("yyyyMM")` converts a year and month (such as a processing month) to the first day of that month. A year and a month stored in two separate fields are not combined: a conversion applies to one field.

### Split tables and finding parts

- The same `DbfReader` reads several parts as one table. Every part's header is compared with the first when the reader opens, before any record, so a bulk load never starts on an inconsistent set. `RecordNumber` counts across parts; each part's checksum is verified when its last record is read, and its file is closed right away. Parts come as file paths or, from streams, as a list of `DbcPart` (a stream and an optional name, `part N` when absent), one list rather than parallel lists of streams and names.
- There is no public way to read a DBF split into parts from streams any more (only DBC parts, as `DbcPart`); DBF parts given by path are still read as one table with `DbSusFile.OpenReader(paths)`.
- `DbSusFile.FindParts` returns the parts of a split table in letter order. Names match ignoring case on every OS; a gap is a `FileNotFoundException` naming the missing part; an unlettered file next to lettered parts is an `IOException`. A missing **last** part cannot be detected locally; the client uses the FTP listing, and does not rely on it alone: it asks the server (`SIZE`/`MDTM`, over the control connection) for the part after the last one listed, and for the file itself when the listing shows nothing, so a stale listing cannot hide a part. A listing counts only when the server confirms its end with a completion reply; FluentFTP 55 otherwise returns what it read as a success, so an unconfirmed listing is a transient failure and is never cached.
- **Numbered parts are a rule of the catalog of the client, not of the core.** For SIASUS-BI the client takes the numbered files as the parts of a table and leaves aside the file without a number of the same state and month. That is what the DATASUS server showed (thirty tables with both, the numbered files the newer ones); no document that was read says it, and it is the author's choice. `DbSusFile.FindParts` does not know numbered parts, and `DatasusClient.FindPartsAsync`, which works from a path, keeps the rules of the core: in a local folder there is no such evidence, and to replace in silence the file the caller named by others is the kind of mistake the core refuses. So the rule is only in the methods that take a dataset: they choose the parts themselves (`NumberedPartNaming`) and open them by that explicit list. A part number is an integer from 1 on, with no zero in front; a number missing before the last one is a `FileNotFoundException`; a table that has only the file without a number is that file.

### Integrity and database loads

- The checksum can only be confirmed at the end of the data, so database loads should use a transaction or a staging table and commit only after the reader finished without an exception. The reading guide (`docs/reading.md`) shows this.
- Plain FTP plus CRC-32 detects corruption, not tampering.

### Client

- **Paths** are strings relative to a configurable root (`/dissemin/publicos`). URLs, `..`, `.`, empty segments, `\`, control characters and names invalid on Windows or Linux are rejected. For 112 file types the catalog builds them from a dataset, a period and, where the files are by state, a state (see Catalog, below).
- **FTP:** FluentFTP behind an internal interface; explicit `EncryptionMode = None`, raw `SIZE`/`MDTM`, `LIST` forced.
- **Data connections: `PASVEX` (October 2026).** Each data connection sends `PASV`, ignores the address in the reply and goes to `Host`; over IPv6 FluentFTP sends `EPSV` instead. Alternatives: (A) `EPSV`, with a fallback of the client's own to `PASVEX` when `EPSV` is refused with 500, 501, 502 or 522; (B) `PASVEX` only, chosen; (C) FluentFTP's `AutoPassive`, as before, with the risk documented. Reasons: a hostile or misconfigured server cannot send the client to another address; the command sent to the DATASUS server stays `PASV`, as it was with `AutoPassive`; the client depends neither on FluentFTP's `AutoPassive` fallback, which FluentFTP 55.1.0 changed, nor on FluentFTP's internal state; and it is the least code. In FluentFTP 55, `EPSV` and `PASVEX` both connect to `Host`, so A would not have chosen the address more safely than B. Evidence: an experiment with FluentFTP 55.0.0 and 55.1.0 alone, against a loopback server whose `PASV` reply named another loopback address: `AutoPassive` and `PASV` followed the named address and `PASVEX` went to `Host`; the explicit modes behaved the same in both versions; 55.1.0 no longer fell back from a refused `EPSV` to `PASV` in a case where 55.0.0 did (see Data connections in [Compatibility](https://github.com/euclydesuchoas/dbsus/blob/main/docs/compatibility.md)). A read-only check against the DATASUS server: `EPSV` and `PASV` both worked end to end, the `PASV` reply named the address of the control connection, and listings with FluentFTP 55.0.0 in `EPSV` and in `PASVEX` mode succeeded. In October 2026 the server's `FEAT` reply did not list `EPSV`, and the server accepted both `EPSV` and `PASV`. Also in October 2026, the client with `PASVEX` downloaded a small file from the DATASUS server in full and resumed a partial download of it with `REST`; the two files were identical and their CRC was checked.
- **Concurrency:** the client is thread-safe; a pool lends at most `MaxConnections` connections (default 2, maximum 4).
- **Retries:** transient failures only (socket errors, timeouts, FTP 4xx, truncated transfers), exponential backoff with jitter capped at 30 s; `550` to a request for a file is `FileNotFoundException`. A listing refused with a permanent reply (5xx, `550` included) is `DatasusRequestRefusedException`, never retried and never a missing file: FTP uses `550` both for a folder that does not exist and for one that may not be read (the folder of preliminary data is the one exception, described with the catalog). FluentFTP 55 takes a `550` to `LIST` for an empty folder and returns no entries, so the client reads the reply itself (reproduced against a loopback server, October 2026).
- **Unexpected exceptions from FluentFTP** are transient failures too. FluentFTP 55.0.0 throws a `NullReferenceException` from a listing when the server has closed the control connection without notice: it retries the listing on the stream it has just closed (reproduced against a loopback server, October 2026). Only the calls into FluentFTP are wrapped, so that an exception of this library's own code is never retried or hidden; cancellation, invalid arguments, and the exceptions FluentFTP throws by design keep their own handling. The connection is not reused, and after the last retry the original exception is the inner exception of `DatasusRetriesExhaustedException`. `OnRetry` reports each retry (a description of the operation for people to read, the remote path, the attempt, the wait, the failure); its exceptions are ignored.
- **Failures** have their own types, all deriving from `IOException`. The abstract `DatasusTransferException` carries `Attempts`, `FtpReplyCode` and `RemotePath` (always set, `/` for the root), and is the common base of three:
  - `DatasusRetriesExhaustedException`;
  - `DatasusRequestRefusedException`;
  - `DatasusRemoteFileChangedException`, for the reader without a download.

  `InsufficientDiskSpaceException` is a type apart, deriving from `IOException` directly. A permanent FTP reply is never retried.
- **Timeouts and cancellation, intended for every runtime; verified on .NET 10 and .NET Framework 4.8.1.** On .NET Framework, FluentFTP's asynchronous reads observe neither its read timeout nor the cancellation token (they rely on a token that `NetworkStream.ReadAsync` there ignores once a read has started), so a server that stops answering would block forever. There the client uses FluentFTP's synchronous client, whose reads enforce the timeout, on the thread pool; elsewhere the asynchronous one. Canceling closes the connection's sockets, which is meant to end any pending read on every runtime; each read of a download is limited to `ReadTimeout` by the client itself; a connection closed by force is never returned to the pool. A canceled download leaves no cache entry, only its `.partial` file, from which the next download resumes (see Cache for when it starts over instead). Opening a transfer that resumes, from `PASV` to the reply to `RETR`, has a limit of its own, 5 seconds: a server that leaves a command of that opening unanswered would otherwise hold the attempt until `ReadTimeout`, or until the operating system gives up on a command it never sees acknowledged. Since this relies on FluentFTP's protected connection hooks, on .NET Framework the client checks that FluentFTP reported each connection (after connecting; before a download can be read; right after a listing, which FluentFTP reads in the same call) and otherwise refuses that FluentFTP version with a `NotSupportedException`, not retried. FluentFTP is declared as a minimum (55.0.0) without an upper bound; a weekly workflow tests the newest release.
- **Transport messages** name the step (connecting, listing, reading the size and date, opening for reading) with the host and port. FluentFTP reports a failed TCP connect the same way for the control and the data connection, so the message does not say which one failed: it says whether FluentFTP reopened the control connection during the step and, when the step opens a passive data connection, gives a blocked passive connection as a possible cause only.
- **Cache:** `<cache>/<remote path>/<file>/<size>-<MDTM>/`, one folder per server version, so a new version never overwrites a file a reader has open. Interrupted downloads resume with `REST` when size and time are unchanged, a `.partial` file of an earlier call or another process included. Only after an attempt of the same call failed to open a resumption (its limit ran out, a reset, another failure of the opening) is the `.partial` file deleted and the download started over from byte 0, without `REST`, once the size and time are checked again, as before every attempt with a `.partial` file: when it holds at most 16 MiB (reading that again costs less than another resumption that may fail too), or on the last attempt `MaxRetries` allows; otherwise `REST` is tried again. A failure in the middle of a transfer that opened is no evidence against `REST`: starting over then would only throw progress away on a link that drops now and then. With `VerifyOnDownload` (default) the file is fully decompressed and its CRC checked before entering the cache. Per-entry lock files (`FileShare.None`; `flock` on Linux/macOS) coordinate processes. Old partial files are removed only when older than 24 hours and unlocked; with a size limit, least recently used entries are evicted, never one in use.
- **Without a cache:** each download goes to a folder of its own, `DbSus-<32 hex digits>`, created directly in the system temporary directory (no parent folder shared between users or processes, which on Linux and macOS the sticky bit of `/tmp` keeps others from renaming or deleting) and only if nothing has that name; it is deleted, with its file, when the reader is done. Permissions: on the `net10.0` build outside Windows the folder is created readable by its owner only (0700, `Directory.CreateDirectory` with a `UnixFileMode`); the `netstandard2.0` and `net472` builds have no such API and leave the system's default permissions (usually 0755 on Linux), with no reflection to reach it. Clean-up of what is left behind (a process that was killed, a file from `DownloadAsync`): only folders named that way, older than 24 hours, holding their `entry.lock` and at most the downloaded file and its `.partial`, none of them open, with no subfolder and no link, or holding nothing at all; links are never entered; a failure on one folder leaves it and the clean-up goes on, and it never throws; it runs on the thread pool, so that it never delays a download; it never touches the folder of the download that started it, which it leaves out by name, not by the clock, since it runs next to that download and may reach that folder at any point. Earlier versions used a shared, predictable `DbSus/downloads`; its folders are still cleaned up the same way for one more version (October 2026). Residual limit: in a `/tmp` shared with other users, one of them could plant old `DbSus-<32 hex digits>` folders and swap one for a symbolic link between the check and the removal; the window is small, the clean-up deletes only files it recognizes, and in a container with a single user this does not apply.
- **Reading without a download (preview, October 2026).** `OpenStreamingReaderAsync` reads a table straight from the server.
  - **It returns a `DbfReader`**, the type `OpenReaderAsync` returns, so code that reads a downloaded table reads a streamed one unchanged. That covers ADO.NET consumers, the comparison of the parts' schemas at opening, and the CRC-32 at the end of each part. A reader type of its own would be more API to keep for the same records.
  - **One connection per reader.** Each reader holds one place of the pool, and its connection, from its opening to its end, because an FTP transfer needs its control connection for its whole length. A reader that gave its place back between reads would have to win one again in the middle of a table, behind other operations, or would keep them waiting.
  - **The limit is `MaxConnections` − 1 readers,** so that one place stays free for listings and sizes. One reader more fails at once instead of waiting, since the place it would wait for may be held by another reader of the same caller.
  - **Each part's body is asked for from byte 0,** dropping the bytes the reader already has (the header read ahead for the parts after the first). `REST` is sent only to resume after a failure. The common path then asks for each file as a download does, and the rules for resuming and for starting over (see Cache) apply to the reader as to a download.
  - **Alternatives set aside:**
    - a reader type of its own, which adds API and changes nothing for the records;
    - a connection taken per part or per read, which could stall a reader behind other operations in the middle of a table;
    - each part's body resumed with `REST` from the end of its header, which would make every opening depend on `REST`.

### Catalog

- **Scope:** 112 file types of SIASUS, SIHSUS, CNES, SIM, SINASC, CIHA, CIH, SISPRENATAL, SISCOLO, SISMAMA, PCE, RESP, ESUSNOTIFICA, PO and SINAN: 43 with one file per state and 69 with one file for the whole country and none by state. A file type enters the catalog only when the server's listings (October 2026) showed one regular folder and name pattern for it and one real file of it, with records, was read; SINAN-INFL is the one exception (see the next item). Other file types that the listings showed are in the paths guide, outside the catalog. The catalog follows the server, not the DATASUS website: the two disagree on when some file types start (`docs/datasus-paths.md` has the table).
- **SINAN-INFL is in the catalog with no known file.** The file transfer page of the DATASUS website lists a SINAN file type `INFL` (*Influenza Pandêmica*); in October 2026 the server had no file of it, and the form of that page returned none. It was first left out for that reason, and the author then decided to have it. *Why:* who knows the list of the website should find every one of its `.dbc` file types here, and an absent `INFL` reads as an oversight of the catalog. *The risk taken:* the folders and the file name are a guess by the pattern of the other 57 of SINAN, and of the name only the stem `INFL` is in a definition file of the server; no file was seen, so the first year, 1999, is the earliest one of the other SINAN file types and not the start of a series; and DATASUS may publish the file in another folder or under another name, in which case the paths built here do not find it. All of this is said where the file type is met: in its documentation, in the paths guide, and in the `FileNotFoundException` of a table not found, which says that no file of it was known. No public member marks it, on purpose: a member for one file type that may yet get its file would be API to keep. *The correction,* if a file appears and does not match, is a change to the catalog.
- **Folders that repeat others stay outside.** Five folders of the server hold `.dbc` files under names that a folder of the catalog also has: `/SINASC/NOV/DNRES`, `/SINASC/ANT/DNRES`, `/SIHSUS/MHJ_14_16`, `/SIASUS/teste` and `/CIH/200801_201012/dados2`, with 1,827 files in the listings of October 2026. No dataset reads them; they are reached with the path as a string. *Why:* a dataset has one folder and one name pattern in each era, and every one of these names is already read from the folder of its file type; a second folder for the same name would leave the catalog to choose between two files with nothing to choose by. *What is known:* the names and the sizes. Of the 1,827 files, 1,488 have the size of the file that the catalog reads under the same name (for 54 of them, named with two digits of the year, the file of the same state and year), and 339 have another: 216 in `/SIHSUS/MHJ_14_16`, 58 in `/SINASC/NOV/DNRES`, 55 in `/SINASC/ANT/DNRES` and 10 in `/SIASUS/teste`. *What is not known:* what the files hold, why the sizes differ, and which of two files of one name is the one to use; no file of these folders was opened. The files whose names fit no name pattern of the catalog stay outside as well: the four with `IG` in the place of the state, the five placeholders of the CNES folders, `LERBR19.dbc`, `RESPBR.dbc`, `DNEX25.dbc` and `DNEX26.dbc`. The paths guide names each of them.
- **Coverage is counted.** In October 2026 every `.dbc` file of the saved listings (246 folders, listed from 2026-10-10 to 2026-10-12) was offered to the name readers of the catalog, those of each era of each dataset whose folder is the folder of the file. Of 195,263 files, 193,423 are read by one dataset and none by two, and 1,840 are read by none, in eleven groups, every one named in the paths guide. One dataset, SINAN-INFL, reads none of them: the listings had no file of it. The list of file types of the file transfer page of the DATASUS website was compared with the catalog as well. *Why count:* that the catalog has every file is a claim about the server, and only its listings can back it. It is a count of names, not of content, and it holds for what the listings and that list showed on those dates; the paths guide ("Coverage") says what was not checked. The count is meant to be repeated on fresh listings before a release. On 2026-10-14, before the release, the root of `/dissemin/publicos` and the 47 folders with `.dbc` files were listed again: the root had the same 25 folders, and the 47 held 195,267 `.dbc` files, four more than in October, all of them new files of CIHA; 193,427 are read by one dataset and none by two, and the same 1,840 are read by none, in the same eleven groups.
- **Shape, never availability.** A dataset checks that a period is a month for a monthly file type and a year for a yearly one, and that the state is one. It never checks whether the file exists: DATASUS publishes late, leaves gaps and does not have every state in every period, and constants about that would go out of date.
- **Eras.** A dataset is a list of eras: a range of periods with one folder and one name pattern, because DATASUS changed folders, prefixes and the digits of the year over time. Nine datasets have two eras, the one in use now and the one before it (SIASUS-PA, SIHSUS RD, SP and RJ, SIM DO, DOEXT, DOFET and DOINF, and SINASC-DN); the others have one. An era starts where its folder starts, not at its first file (SIM-DOREXT starts in 1996 with its folder, and its first file is of 2013; a folder with no date in its name starts at the first file listed): `FirstPeriod` is the start of the oldest era, and a period before it is an `ArgumentOutOfRangeException`. The hundred years that a two-digit year can name are counted in each era: the same name is 2007-12 in the older SIHSUS folder and would be 2107-12 in the one in use now. The limit is of every name with two digits of the year, monthly or yearly (PCE, RESP, ESUSNOTIFICA-DCCR, the five SIM file types for the whole country only and every one of SINAN), and not of the names with four. The eras themselves are not public.
- **The whole country.** Four datasets have, beside the files of the states, one file for the whole country (SIM-DO, SINASC-DN, PCE and RESP), and 69, the 58 of SINAN among them, have a file for the whole country and none by state; they are datasets like the others, and `Coverage` says which files a dataset has. The file for the whole country has methods of its own (`GetNationalPath`, `FindNationalTableAsync`, `ListNationalTablesAsync`, `OpenNationalReaderAsync`) and no member of `DatasusUf`, whose values are the IBGE codes of the states: a call that forgets the state must never open the file for the whole country, which can be tens of megabytes. No method returns both kinds. A dataset without the files asked for is a `NotSupportedException` from `DatasusDataset` (the object does not have them) and an `ArgumentException` from the client (the dataset is an argument). The name of the file for the whole country belongs to the era, like the name of the file of a state, and has no part letter.
- **Final and preliminary data.** Which years SIM and SINASC still publish as preliminary changes, so nothing about it is constant in the code: a dataset gives the candidate paths in order, final first, and the client asks the server. `OpenReaderAsync(dataset, uf, period)` opens final data only, so that preliminary data is never read by accident; preliminary data is opened from a `DatasusTableInfo`, where `IsPreliminary` is in plain sight. The folder of preliminary data is optional, since a source may stop having one: a `550` to its listing, and no other reply, is taken as there being no such folder. Because the same `550` is the answer for a folder that may not be read, a table not found then fails with a `FileNotFoundException` that says that the folder could not be listed and carries the reply; `ListTablesAsync` has no way to say it and returns the tables of the folder of final data.
- **Listing or asking.** `ListTablesAsync` is one directory listing per folder and inherits its limits (a partial listing omits files without any error; listings are cached). `FindTableAsync` asks the server for the file itself, as `FindPartsAsync` does, and is the reliable way to know whether a table exists.
- **Letter case.** Paths are built in upper case with a lower-case extension, while the server lists some names otherwise. The server ignored case in October 2026: for a file listed as `DORR2011.DBC`, `SIZE` answered `213` with the same size under that name and under `dorr2011.dbc`. Tables are nevertheless opened under the name the server lists, because the cache is keyed by the remote path and one file must not be cached under two spellings.
- **Names.** `DatasusDataset` and `DatasusCatalog`, not `Dataset`: one capital letter away from `System.Data.DataSet`, in a library whose reader is a `DbDataReader`; and the prefix matches `DatasusClient` and `DatasusFileInfo`.
- **`DatasusUf`** members are named by the abbreviation that file names carry, and their values are the IBGE codes of the states. There is no zero member: `default(DatasusUf)` is rejected rather than named.
- **`DatasusPeriod`** is a month or a year. A year is never equal to a month, and a year sorts before its own months.
- **`OfficialName` is in Portuguese,** a deliberate exception to the rule that everything in the code is in English: it is the name under which DATASUS publishes the file type, a proper name, kept as DATASUS spells it (including `Confeção`).
- **`OfficialName` may be `null`.** For three file types (SIHSUS CH, CM and MT) no name was found: the file transfer page of the DATASUS website does not list them, and the documents and definition files of the server that were searched do not name them. The property is `null` for them. No name is made up: one written here would pass as the name DATASUS publishes.
- **Files read.** By October 2026 one real file of 111 of the 112 file types, with at least one record, was read with DbSus: decompressed, its CRC-32 checked, and every field of every record read. Of SINAN-INFL none was read, because no file of it was found on the server. It was usually a small and old file, and some held a single record; for some file types the first files tried had a header and no record, and another was read (the paths guide says which). From the folders of preliminary data, two files of states were read in the same way in October 2026, found and opened through the catalog on the server: SIM-DO and SINASC-DN of Roraima, both of 2026; 25 of the 65 SINAN files read were in its folder of preliminary data. Of each of the nine older eras, one file with records was read in the same way in October 2026. Of the four file types that have files by state and a file for the whole country, the file for the whole country of PCE and of RESP was read in the same way, one each; those of SIM-DO and SINASC-DN had only their headers read, six in all. In 12 SINAN files, some `N` and `D` fields did not convert in some or all records: those fields were read as bytes and each file was read to its end, and the twelve were then read again with `DbfReadOptions.UnconvertibleValues`, through the client. Of SIASUS-BI, a file without a number and one numbered part were read, and the header of another part; no complete set of numbered parts was read. For four tables that have both the file without a number and numbered parts, the record counts of the headers were compared: they are equal in one, and in the other three the numbered parts have more records (the paths guide has the numbers). That says nothing about other periods or other files. The paths guide says, in a column of its tables, what was checked of each file type and of each older era.

## Performance

BenchmarkDotNet, Release, net10.0, AMD Ryzen 9 9950X3D, one large SIA-PA file (126 MB DBC, 1.17 GB DBF, 2,956,469 records × 60 fields):

| Benchmark | DBF throughput | Allocated per record |
|---|---|---|
| Decompress only | 847 MB/s | 0.05 B |
| Decompress + read records | 730 MB/s | 0.06 B |
| + 3 typed getters | 661 MB/s | 0.06 B |
| + 2 converted `C` fields | 637 MB/s | 0.06 B |
| Every value of every field (`GetValues`, boxed) | 295 MB/s | 1,867 B |

Decompression dominates typical use: it consumed the compressed file at about 78 MB/s (126 MB in about 1.6 s; see `docs/performance.md`). When files come from the DATASUS server through `OpenReaderAsync`, the client downloads each one, or every part of a table, to a file before the first record is read, so the time of the network and the time of decompression add up; and with `VerifyOnDownload` (the default) a `.dbc` is decompressed once when its download ends, to check its CRC-32, and again when it is read. The reader without a download (`OpenStreamingReaderAsync`, preview) decompresses the data as it arrives, once, checking the CRC-32 at the end of each part. No figure in this guide includes either.

## Testing

- **Oracle:** `tools/oracle` (Docker, `pyreaddbc` 2.0.4) records SHA-256 and size of each `.dbc` and its `.dbf` in `tests/data/expected.json`, so tests and CI do not need the oracle.
- **Decoder:** the upstream `blast` test vector, byte-for-byte agreement with the oracle on real files (including outputs of about 2 GB), decoding with random chunk sizes, and per-path coverage measurements. No available input uses Huffman-coded literals or the 2 KiB dictionary, so an encoder that exists only in the tests (`ImplodeEncoder`) writes streams in every mode: raw and coded literals, the three dictionary sizes, the boundary lengths and distances, and copies that overlap their own output.
- **Decoder against its previous version:** the decoder of version 0.1.0-preview.1 is kept in the tests as a second oracle (`ReferenceBlastDecoder`), and the production decoder runs side by side with it, read after read, with random destination sizes and input buffers down to one byte. On the encoder's streams, on every truncation of small streams and on one-byte changes of them, and on the real files available locally, both must return the same bytes, or throw the same exception with the same message, and agree after every read on the compressed bytes consumed and the end of the stream. The real files are compared on their first 64 MiB of output; setting the environment variable `DBSUS_FULL_DIFFERENTIAL` to `1` compares them whole.
- **Allocation per record:** on net10.0, `GC.GetAllocatedBytesForCurrentThread` around a loop over 999 records must not move. A background GC that suspends the threads during the loop makes the unused rest of the thread's allocation context count as allocated, so each measurement is taken up to three times, each with its own warm-up, and one of them must allocate nothing; an allocation per record shows in all three.
- **No microdata in the repository.** Samples are fetched by `tools/fetch-samples` into a git-ignored folder and checked against `expected.json`; tests that need them skip themselves when absent. The only committed data files are two small CNES tables with establishment-level data only (`tests/data/fixtures`).
- **Synthetic DBCs** built in memory (literal-only implode, independent CRC-32) cover the wrapper in CI.
- **Cross-process locks** are tested with two real processes on Windows (.NET 10 and .NET Framework) and Linux.
- **Client:** an in-memory fake server injects failures (dropped transfers, 421, republished and corrupt files, low disk space, cancellation, concurrency). Tests against the real server run only on request.
- **Package consumers in CI:** an outside application restores the packed packages and checks which build it loaded (net8.0 → `netstandard2.0`, net10.0 → `net10.0`, net481 → `net472`), runs again with the oldest accepted dependency versions pinned (NU1605 guard), and once more built with SDK 8, which, unlike SDK 10, does not prune framework packages from the restore.

## Packaging

- Each package ships `LICENSE` and `README.md`; `DbSus` also ships `THIRD-PARTY-NOTICES.md`. Symbols go to `.snupkg` with SourceLink; package validation is on.
- Packages are published only from CI builds (`ContinuousIntegrationBuild`), whose PDBs and DLLs carry `/_/` source paths instead of machine paths.
- Tags by purpose: `datareader` and `ado.net` only on `DbSus` (its ADO.NET integration); `ftp` and `download` only on `DbSus.Client`; the rest is shared.
- **Public API tracking** (Microsoft.CodeAnalysis.PublicApiAnalyzers): each library lists its public API in `PublicAPI.Shipped.txt` (what a published version contains) and `PublicAPI.Unshipped.txt` (what changed since). The build fails when the code and the files disagree, so every API change shows up in a review as a change to these files. The API is the same on every target framework, so there is one pair of files per project. Until the first release, `Shipped` is empty and the whole API is in `Unshipped`. When a version is published, `Unshipped` moves into `Shipped`; from then on, a removed or changed member appears in `Unshipped` as a `*REMOVED*` line. RS0026 is suppressed until that first move (see the project files).
